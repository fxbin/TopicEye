# Agent Note: 首页首屏服务端直出的口径与约束

Status: implemented — #197（Owner 指示"按实际情况改"），Worker 实施

## Problem

首页原本整页是 `'use client'`，内容列表在 `useEffect` 里才拉：首屏 HTML 里只有壳和一个
「加载中」 spinner，**一张内容卡片都没有**。首屏最大文本块（第一张选题卡的标题）必须等
「JS bundle → hydration → 客户端取数 → 渲染」整条链路走完才画得出来——LCP 被客户端链路拖着。

筛选栏约占 340–400px，首张选题卡在折线之上，所以它就是 LCP 元素。

## Decision

首页改成服务端组件，首屏三份数据（**内容列表 / 分类 / 标签分面**）一次取好直接进 HTML；
客户端只在筛选条件变化时重新取数。

**三份数据必须一起直出**：分类与标签 chips 行如果客户端再取一遍，内容画出来之后 chips 行
会二次变化——那是净新增的 CLS。

## 三条硬约束（下次改这块必看）

### 1. 服务端与客户端必须用同一个 page_size

浏览快照（`feed_snapshot`）只钉住列表顺序，**不钉页边界**；后端按**请求里的 page_size**
切片（`rows[(page-1)*page_size : page*page_size]`）。两边不一致，客户端的「加载更多」会
跳过中间那几条。口径由 `frontend/src/lib/feed-query.ts` 的共享常量保证。

### 2. 每页条数与首屏 payload 线性相关

实测（本地起后端连开发库真实数据 + 前端生产构建，`curl` 首页统计）：

| 每页条数 | 首屏 HTML | 其中 RSC flight |
|---|---|---|
| 40 | **544KB** | 199KB |
| 12 | **142KB** | 18KB |

40 条时弱网下光下载就比「先拿骨架、再取数据」更慢。首屏实际只看得到 3–4 张卡片，
**12 条**足够。这条决定了每页条数从 40 降到 12——是可见的行为变化（「加载更多」每次加
12 条），要改回 40 只改那一个常量。

### 3. 服务端取数失败必须能降级

超时或后端不可达时返回 `ok=false`，客户端照旧自己取，行为与改造前一致。服务端取数有
3s 超时；首屏 HTML 不因后端故障而挂住。

## 登录态怎么跟着走

服务端转发 HttpOnly auth cookie 取数（与 `lib/server-prefetch.ts` 同一套做法）；
客户端用服务端给的 `userId` 判断「用户变了要重新取」。`prefetchInitialData` 用 React
`cache()` 包住，与根布局共用同一次请求——不额外打后端。

## fade-in 只动 transform

`globals.css` 的 `fade-in` 原来从 `opacity: 0` 起步：opacity 为 0 的元素不是 LCP 候选，
首屏内容在动画期间不具备候选资格。改成只动 transform，opacity 全程为 1，元素从第一帧
就可选，且不依赖 Chrome 对 opacity 阈值的具体判定。9 个页面共用这个动画，滑入效果保留。

## 实测口径（不是 LCP 数字）

本地没有真实浏览器与真实流量，**没测到 LCP 本身**。测的是「内容出现前要下载的字节数与
串行阶段数」这个可量化代理：

| | 改造前 | 改造后 |
|---|---|---|
| 首屏 HTML | 31.0KB | 142.2KB |
| 直出的卡片 | 0 | 12 |
| 内容出现前的下载总量 | 31KB + 701KB JS + 188KB API JSON ≈ 920KB，3 段 | 142KB，1 段 |

真实 p75 LCP 要上线后由 #179 建好的监控面（大盘 `/dashboard` 的「前端体验」Tab）来看。

## 遗留

- 首屏 HTML 从 31KB 涨到 142KB：省掉的是 JS + API 两个串行阶段，但首屏字节变多。
  弱网下的净收益需要真机验证。
- 「加载更多」每次 12 条（原 40 条），交互手感有变化。
- 分类/标签 chips 在服务端直出后不再随客户端刷新，只在筛选变化时随列表一起更新。

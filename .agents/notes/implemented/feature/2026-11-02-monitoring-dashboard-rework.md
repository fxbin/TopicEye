# Agent Note: 监控大盘改版与体检判定口径合同

Status: implemented — #209（Owner 指派「改吧，并把入口归入后台管理」）

## Problem

内置监控大盘 `/dashboard`（`backend/app/api/dashboard.py` 直出 HTML）在用户端已经存在，但有三个问题叠在一起：

1. **没有入口**：页面本身能访问，后台侧边栏里却找不到它。运维要监控大盘只能手动敲 `/dashboard`，等于没有。
2. **不像这个产品**：深海军蓝霓虹皮肤 + 7 张等权 KPI 卡，与 TopicEye 其它页面的浅底橙色系完全不是一套东西；数字彩虹化但无语义；空态占掉大半首屏；没有「看某项证据」的动作。
3. **判定逻辑藏在 JS 里、零测试覆盖**：阈值、单位换算、枚举大小写全在前端各写一份，错了没有任何东西会报警。

第 3 点是这次真正挖出东西的地方。在改版过程中实测发现三个真实缺陷（详见「独立复核与自查发现的三处」）——它们共同指向一个结论：**判定口径必须放在服务端**。

## Decision

### 一、判定口径的真源放服务端（架构决定）

新增 `backend/app/services/metrics_checks.py`：体检项的定义（阈值、单位、严重程度映射、「有没有样本」的判据）与判定都在这里，前端只负责把结论画出来。

`GET /api/v1/metrics/checks` 返回每项的当前值、展示串、阈值说明、状态与一份计数汇总。

为什么不能留在前端 JS：

| 前端自己判会出的错 | 服务端为什么不会 |
|---|---|
| 接口返回延迟是**秒**、阈值按**毫秒**读 → P95 检查永远不触发 | 服务端同时持有值与阈值，换算只有一处 |
| 熔断器状态是小写枚举 `closed/open/half_open`，写错大小写就把熔断判成「正常」 | 枚举是服务端自己的定义，映射与取值同源 |
| LLM 一次都没调用时成功率是 **0%**，拿去比阈值就成了「严重」 | 服务端知道分母是 0 还是真有 0 次调用 |

「没有样本」和「样本值是 0」的区别只有服务端能做，所以它属于服务端。

沿用本仓库已有的做法：前端体验指标的阈值与 p75 口径同样真源在 `web_vitals_service.py`（见 [前端体验指标观测合同](../feature/2026-10-31-web-vitals-observability-contract.md)），两处口径归属一致。

### 二、改版方向：先给结论，再给证据

新版大盘（仍是后端直出 HTML，不引前端框架、不引 CDN）：

- **首屏只有一个主角**：顶部「系统判定条」——一句话结论 + 超标项直达按钮。
- **体检表**取代等权 KPI 卡：8 项检查，每行给「指标 / 当前值 / 阈值 / 迷你趋势 / 状态」，点行就地展开趋势大图与相关日志。
- **色彩只三档**（灰 / 橙 / 红），语义化；数字用等宽表格数字。
- **趋势图下移**，首屏不再被图表挤满；空态给「下一次采样时间」而不是一片空白。
- 左墨色栏 + 右工作区，与后台壳同一套视觉语言。

### 三、入口归入后台管理

> 此节记录当时的入口选择；当前导航方式已由[后台内嵌与前后台跳转合同](2026-11-02-dashboard-admin-navigation.md)替代。数据判定与图表口径仍以本文为准。

`frontend/src/lib/admin-nav.ts` 的唯一清单新增「监控大盘」（`/dashboard`，系统组）。它是**壳外独立页面**：后端直出 HTML，经 `next.config.js` 的 rewrite 以同源暴露。

因此清单里新增 `standalone` 标记：

- `inShell: false` —— 那个页面没有壳内顶栏，不进面包屑（否则顶栏会对着一个不存在的壳说错话）。
- `standalone: true` —— 侧边栏用原生 `<a>` 整页跳转，**不能用 Next 客户端路由**：它要的是 RSC 载荷，后端给的是整页 HTML。

这推翻了 [前端体验指标观测合同](../feature/2026-10-31-web-vitals-observability-contract.md) 里「扩展它避免了新增导航项、面包屑映射与 admin 壳测试」这条**便利性理由**（观测面板仍落在大盘，这点不变）。理由：Owner 指出监控界面根本没有入口——没有入口的便利性是假的。

## Alternatives considered

- **把大盘搬进 admin 壳（Next 路由 + iframe）**：壳内顶栏、面包屑、导航全部现成。否决：大盘是自带左栏的全屏页面，套进壳里会变成双层导航；iframe 还要额外处理加载态与滚动同步。
- **在服务端算好的同时，前端再算一遍做二次校验**：否决。两份口径必然漂移，而这次的三个缺陷正是「前端猜服务端语义」造成的。
- **保留 `fmtMs` 那种「猜单位」的写法**：否决。`fmtMs(s)` 靠 `s<1` 判断这是秒还是毫秒，1.5 秒会被显示成「1.50ms」。改成一律按毫秒入参、单位只由服务端下发。

## Consequences

- 多一个端点 `/api/v1/metrics/checks`；判定逻辑离开前端，前端改动需要同步服务端。
- 大盘自身轮询 `/api/v1/metrics/*` 会计入自己的请求计数——这是自观测系统的固有现象，已在快照数据里如实呈现。
- 前端拿到的 `unit` 是唯一单位来源；新增体检项时，服务端加定义 + 客户端加一条趋势映射即可，判定不用碰前端。
- 代价：一次首屏多一个请求（checks 与 snapshot 并行发出，不串行）。

## 独立复核与自查发现的三处（已修，均有回归测试）

1. **熔断器状态大小写**：判定表写的是大写 `OPEN/HALF_OPEN`，而实际值是小写 → 熔断中的实例永远显示「正常」。已改为小写映射，并补「取不到状态时不算正常」的用例。
2. **P95 单位错配**：阈值按毫秒（500/2000），接口值是秒 → P95 检查永远不会触发。已在服务端统一换算成毫秒，补「300ms 合格 / 1500ms 注意 / 2500ms 严重」的用例。
3. **0 被当成「没数据」的镜像错误**：LLM 零调用时成功率 0% 被判成「严重」。已引入 `has_data` 判据（分母为 0 即无样本），显示「—」且不计入通过数。

三条都写进 `backend/tests/test_metrics_checks.py`（纯函数单测，不碰数据库）。独立复核又挖出判定之外的七处，已一并修掉，见下面「独立复核发现的问题」。

## 独立复核发现的问题（已修）

复核者跑了 5 条定向变异（熔断状态大小写、P95 秒→毫秒换算、LLM 零调用当有样本、关掉 `invert` 分支、阈值比较 `>` 改 `>=`），全部被测试抓到——判定规则本身没问题。但复核同时挖出几处**判定之外的错**，都已修：

1. **趋势口径与当前值不是一回事**：错误率那一行当前值是比率，趋势却画累计 5xx 个数；连接池当前值是利用率，趋势画的是已借出连接数。同一行里两个数字说的不是一回事，纵轴还会把「37 次」标成「37.0%」。已改为画 `http_error_rate` / `db_pool_utilization`，与当前值同口径。
2. **前端仍抄了一份阈值与状态映射**：运行时状态卡里自己判「慢查询偏高」「熔断 open」，与服务端判定各执一词（恰好 50 次时两边还不一样）。已删掉副本，状态卡直接用服务端的判定结论；缓存命中率没有行动阈值，改成只显示数值不判档位。
3. **未知枚举值被判成「正常」**：熔断器状态表里没列的状态值默认落到「正常」。已改为默认「待定」，并把已知状态列全（closed/open/half_open）。
4. **阈值文案与实现不一致**：判定是「严格超过才算超标、等于阈值算合格」，文案却写「< 500ms 合格」。已改成 ≤ / ≥。
5. **慢查询拿累计值比固定阈值**：慢查询是进程启动至今的累计计数，跑久了必然「超标」——那是累计量比瞬时量。已改成「每小时多少次」（累计 ÷ 进程运行时长，分子分母都从进程启动算起）。
6. **读不到慢查询计数时回落成 0**：读失败被说成「一次慢查询都没有」。已改为读不到就是读不到，显示「—」。
7. **汇总把「判不出档位」算成「通过」**：有数据但状态不是 ok/warn/crit 的项原先都计入通过数。已单独记为「待定」。
8. **测试自身有两条断言写错**：1500ms 落在 warn 阈值之上却断言合格；空采样时请求速率也无样本（无样本项是三项不是两项）。两条都按实现改正。

**教训**：把判定搬到服务端只是搬走了第一份口径；前端只要还留着阈值、状态映射或另算一份趋势，就会重新长出第二份。**凡是「怎么算」的语义都要走服务端，前端只留「怎么画」。**

## 明确不做

- 不把大盘搬进 Next 页面（见上）。
- 不给体检项加告警推送——`services/metrics_alerting.py` 已有服务端告警，大盘只负责给人看。
- 不做大盘的历史回放与时间游标。
- 不动 `next.config.js` 的 rewrite 机制。

## Verification

- `backend/tests/test_metrics_checks.py`：判定口径单测（无数据、枚举、单位、阈值边界、汇总口径）。
- `make layering`：新 service 与新端点符合分层纪律（判定在 service，端点只取快照转发）。
- `cd frontend && npx tsc --noEmit` 与 `npm run test:coverage`：379 条前端用例全绿。
- 本地起后端实测：四个页签（概览 / LLM 日志 / 应用日志 / 前端体验）渲染正常，无控制台错误；体检行点击可就地展开趋势与日志。
- 可读性：首屏与各页签截图经默认做法检查，对比度不达标项已全部清零（品牌橙/红在小字上另用深色变体）。

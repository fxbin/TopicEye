# Agent Note: 缺陷登记册为什么从「十个维度」收敛为「三项」

Status: implemented — 2026-10-03 同步改 AGENTS.md 与回归矩阵

## Problem

矩阵自 2026-09-27 建立起就要求每条缺陷按「十个维度」登记。实测 2026-10-03 的 14 条：

| 维度 | 实际填写 | 维度 | 实际填写 |
|---|---|---|---|
| 回归测试 | 14/14 | 复现 | 10/14 |
| owner | 14/14 | 复现性 | 10/14 |
| 症状 | 12/14 | 边界 | 11/14 |
| 严重度 | 9/14 | 期望 vs 实际 | 8/14 |
| 环境/前提 | 5/14 | **根因** | **2/14** |

八个维度没填满，**而缺失最严重的恰好是根因**——它正是 #5 当初要求登记的核心理由。不记根因，缺陷修完就不知道下次从哪防。

同时，14 条里 11 条已在 GitHub 关闭，状态信息在 `gh` 一次查询里就有，手工维护状态镜像必然腐烂。

## Decision

1. 登记维度**十个 → 三个**：回归测试（怎么发现下一次）、根因（这次错在哪，指向代码位置）、owner（issue 号）。其余细节以 issue 正文为准，矩阵不重复承载。
2. **顺序反转**：先开 issue，再把条目补进矩阵。原先「先登记再开 issue」导致过 2 条无对应 issue，且 #90 实际是先开的 issue、第二天才补记。
3. 矩阵的定位从「缺陷档案」收窄为「流程基线 + 未关闭缺陷索引」。已关闭条目的状态、PR、修复时间全部交给 GitHub。
4. 早期限期的条目保留原字段，不做追溯改写。

## Alternatives considered

- **保留十个维度，只加一句「尽量填全」。** 否决：这正是现状，规则还在但没被执行。再加一句提醒不会改变行为。
- **把状态也留着，只简化维度。** 否决：状态是唯一真正会持续腐烂的部分。11/14 已关闭说明手工推进状态追不上真实进度。
- **让脚本自动生成矩阵状态。** 暂缓：收益真实但要写脚本 + 接 CI 门禁，属于「有意义的变更」，需单独立 issue。当前规模（14 条、单人项目）下不急，但债已记下。
- **把根因判定搬进 `.agents/notes/`，矩阵只留索引。** 部分采纳：`bug-fix` class 确实承载了这类 why（见 `implemented/bug-fix/`），但矩阵的根因字段保留——两份都留是刻意的冗余，因为根因太重要不值得只存在一处。

## Consequences

- 登记成本从「填十项」降到「写三行」，其中两项在 #88 时已是 14/14 全覆盖。
- 关键在于删掉的是**做不到的要求**。一条 agent 做不到的规则会连带降低它对邻近规则的遵守度。
- 再议条件：条目破 30 条时，状态自动化该上马了。
- **后续（2026-10-03 同日）**：登记册 `docs/quality/regression-matrix.md` 整体删除。§二 的已关闭档案移交 GitHub，§一 跑测安全守则与 §三 九项流程的验证命令并入 `AGENTS.md`。缺陷状态看 GitHub、命令看 AGENTS.md、理由看 `.agents/notes/`，三者不再重叠。

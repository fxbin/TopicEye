# Agent Note: 提示词目录与请求统计分开归属

Status: implemented — #225 确定代码目录真源与场景请求统计归因

## Problem

一条模型请求通常同时使用系统模板、用户模板和动态内容。旧目录按每个模板重复展示同一场景的请求总数，容易把场景用量误认为单个模板或当前版本的用量；目录的旧 scene 也可能与实际请求日志不同。

## Decision

- 代码模板是事实源，数据库只保留可读目录副本。启动同步除了内容哈希，还修复 scene、描述与来源元数据；停用模板不删除历史记录，但退出当前目录。
- 列表每个 scene 只聚合一次请求尝试，分别报告成功、失败、其它状态及日志记录成本。详情展示所属场景所有版本的统计，不能据当前模板哈希归因。
- 有请求但无目录模板的场景仍展示，避免漏掉自定义评测、动态输入或尚未登记的模板。目录未完整同步时显式提示。
- 现有日志缺少模板组合、版本、独立业务请求与响应缓存身份。本次不迁移数据库，不推算重试次数、缓存命中或单版用量；请求成功也不代表业务结果验证成功。

## Alternatives considered

把场景统计复制给每份模板、或从当前代码版本反推历史版本调用均不采用。数据库在线编辑模板也不在本合同内，不能把可读目录当成生效的配置。

## Consequences

要支持按模板组合或版本归因，需另行设计请求级身份、缓存与重试语义，以及版本发布/回滚和迁移合同。当前统计只能用来诊断场景流量、请求状态与成本，不能直接评判提示词质量。

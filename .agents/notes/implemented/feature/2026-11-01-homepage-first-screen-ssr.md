# Agent Note: 首页首屏服务端直出的口径与约束

Status: implemented — #197（Owner 指示"按实际情况改"），Worker 实施

## Problem

首页原本整页是 `'use client'`，内容列表在 `useEffect` 里才拉：首屏 HTML 里只有壳和一个
「加载中」 spinner，**一张内容卡片都没有**。首屏最大文本块（第一张选题卡的标题）必须等
「JS bundle → hydration → 客户端取数 → 渲染」整条链路走完才画得出来——LCP 被客户端链路拖着。

筛选栏约占 340–400px，首张选题卡在折线之上，所以它就是 LCP 元素。

## Decision

首页改成服务端组件，首屏三份数据（**内容列表 / 分类 / 标签分面**）一次取好直接进 HTML；
客户端只在筛选条件变化时重新取数。

**三份数据必须一起直出**：分类与标签 chips 行如果客户端再取一遍，内容画出来之后 chips 行
会二次变化——那是净新增的 CLS。

## 三条硬约束（下次改这块必看）

### 1. 一页 40 条，服务端与客户端必须一致

浏览快照（`feed_snapshot`）把 **`page_size` 绑进了摘要**——后端算摘要用的
`ContentListCacheParams.key` 里含 `page_size`（见 `app/services/content_list_cache.py`）。
所以同一次浏览里换 `page_size` 会被判成「内容顺序已更新」而 **409**。

后果：**「首屏直出 12 条、后台用 40 条补齐」这条路不存在**——补齐请求带着 12 条的快照
去要 40 条，必然 409。想让页大小可变，只能整条链（服务端首屏 + 客户端续页）一起改。

口径由 `frontend/src/lib/feed-query.ts` 的 `FEED_PAGE_SIZE` 保证。

### 2. 每页条数是用户可见的行为，别随手改

每页 40 → 12 会让「加载更多」每次只加 12 条。Owner 明确认为这是**体验退化**——
首屏快一点不值当。首屏 HTML 的大小是技术问题，页大小是产品问题，两者不该混在一起动。

### 3. 服务端取数失败必须能降级

超时或后端不可达时返回 `ok=false`，客户端照旧自己取，行为与改造前一致。服务端取数有
3s 超时；首屏 HTML 不因后端故障而挂住。

## 登录态怎么跟着走

服务端转发 HttpOnly auth cookie 取数（与 `lib/server-prefetch.ts` 同一套做法）；
客户端用服务端给的 `userId` 判断「用户变了要重新取」。`prefetchInitialData` 用 React
`cache()` 包住，与根布局共用同一次请求——不额外打后端。

**SSR 路径下 `reportContentTotal` 要单独报一次**：列表取数被跳过了，侧边栏的内容数
徽标否则会一直是 0。

## fade-in 只动 transform

`globals.css` 的 `fade-in` 原来从 `opacity: 0` 起步：opacity 为 0 的元素不是 LCP 候选，
首屏内容在动画期间不具备候选资格。改成只动 transform，opacity 全程为 1，元素从第一帧
就可选，且不依赖 Chrome 对 opacity 阈值的具体判定。9 个页面共用这个动画，滑入效果保留。

## 实测口径（不是 LCP 数字）

本地没有真实浏览器与真实流量，**没测到 LCP 本身**。测的是「内容出现前要下载的字节数与
串行阶段数」这个可量化代理（gzip 后实际传输，同一后端、同一数据、同一生产构建）：

| | 改造前 | 改造后 |
|---|---|---|
| 首屏 HTML | 5.8KB | **94.7KB** |
| 直出的卡片 | 0 | 40 |
| 内容出现前的传输总量 | 5.8KB + ~200KB JS + ~30KB API ≈ **236KB，3 段** | **94.7KB，1 段** |
| 「加载更多」每次 | 40 条 | 40 条（不变） |

原始 HTML 从 31KB 涨到 545KB，但里面全是重复的 Tailwind 类名，gzip 后只有 94.7KB。

真实 p75 LCP 要上线后由 #179 建好的监控面（大盘 `/dashboard` 的「前端体验」Tab）来看。

## 遗留

- 首屏 HTML 从 5.8KB 涨到 94.7KB（gzip 后）：省掉的是 JS 与 API 两个串行阶段，
  弱网下的净收益需要真机验证。
- 分类/标签 chips 在服务端直出后不再随客户端刷新，只在筛选变化时随列表一起更新。
- 客户端的 hydration 要处理 40 张卡片（改造前是 0 张、SSR 空壳），首屏 JS 解析与
  hydration 的开销变了，未实测。

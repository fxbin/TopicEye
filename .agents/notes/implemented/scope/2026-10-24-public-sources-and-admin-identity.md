# Agent Note: 信源透明度与管理员动作不扩展用户身份权限

Status: implemented — 基线 738ac61 核实现有路由与管理员创建逻辑；#151 补录范围理由

## Problem

公共信源展示、管理页面拆分、管理员创建用户分别来自旧方案。展示信息、维护共享资源和取得另一个账号的登录身份，是三种不同的权限；不能因页面被放进某个路由组就混同。

## Decision

普通用户查看公共信源是了解推荐依据，不等于修改、删除或触发公共抓取；公共/私有层以 [归属决策](../architecture/2026-10-24-data-ownership-and-legacy-adr.md) 为准。
管理导航和布局帮助识别入口，服务端鉴权仍是授权边界。[管理员创建用户](../../../../backend/app/api/v1/users.py) 由管理员担保创建，不创建被创建用户的 session，登录由用户另行完成。

## Alternatives considered

- 为查看公共信源默认复制一份私有源：不采用该旧提议，复制会带来重复抓取；关注/订阅需求应另作产品验证。
- 只藏前端按钮或改路由就认为权限已隔离：不采用，API 仍须验证操作者和资源范围。
- 创建用户后自动登录该账号：不采用，管理员管理身份不能顺带成为该用户会话。

## Consequences

旧圆桌的字段数、一次加载阈值、状态灯样式是历史 UI 建议，模拟角色并非真实用户访谈，不据此固化产品参数。
入口见 [我的信源](../../../../frontend/src/app/sources/me/page.tsx)、[管理导航](../../../../frontend/src/lib/admin-nav.ts)；回归入口 [users admin](../../../../backend/tests/test_users_admin.py)。本次未运行账号创建或对外投递。
